# World Data Container Design

This document designs the container that holds the core's world state, the "data container
for world" item in `TODO.md`. It is a dcon-style structure-of-arrays (SoA) container,
generated by C++26 reflection. SIMD, CPU parallelism and GPU upload through snapshots are
part of its design from the start.

Status: designed, not implemented. The only built parts are the chunk constant (§4), the
column padding rule (§3) and the cap constants (§2.1), all in the `sim_estab:limits` module
(`design_limits.md` §3, §4). The toolchain claims below were verified in the build container,
on GCC 16.1 with the `gnu26` profiles.

The build provides what this document assumes. Every target compiles at `CXX_STANDARD 26`
with `-freflection` and `-march=x86-64-v3`. The exported package passes all three flags on
to consumers, including through `IMPORTED_CXX_MODULES_*`, which targets that import modules
recompile against. The flags are set in `target_set_cxx_standard()` and
`target_set_arch_baseline()` (`src/libsim_estab/cmake/cpp_standard.cmake`).

Terms are defined in [glossary.md](glossary.md). Related designs: `design_engine_core.md`
covers the two-domain architecture, determinism rules, parallelism (§4), the SoA container
(§4.5) and build-order step 3. `design_python_api.md` covers snapshot array views (§7.2).
`design_modding.md` covers mod tiers; the container's mod surface is §7 below.

## 1. Prior art: schombert/DataContainer (dcon)

[DataContainer](https://github.com/schombert/DataContainer) calls itself "more than an ECS,
less than a database". It is the data backbone of [Project
Alice](https://github.com/schombert/Project-Alice), a reimplementation of Victoria 2. That
makes it a shipped, heavily parallel economic grand-strategy simulation, and the closest
existing system to what the engine core needs.

### 1.1 How it works

dcon is a code generator, not a template library, which keeps compile times reasonable. It
reads a small DSL file and emits one C++ header containing a `data_container` class:

```
object{
    name{pop}
    storage_type{contiguous}        # or erasable / compactable
    size{10000}                     # or expandable
    property{ name{wealth} type{float} }
    property{ name{flags}  type{bitfield} }
}
relationship{
    name{employment}
    link{ object{pop}     name{worker}   type{many} }
    link{ object{factory} name{employer} type{unique} }
    property{ name{wage} type{int32_t} }
}
```

### 1.2 What it provides

dcon generates storage, an access API, relationships and serialization from the DSL. It also
ships a SIMD library.

- **SoA storage**: one array per property, never AoS. Handles are strongly typed **tagged
  ids** (2–4 byte indices). `fatten()` gives member-style access for convenience, and is
  explicitly not for bulk storage.
- **Generated API**: `pop_get_wealth(id)`, `pop_set_wealth(id, v)`, `for_each_pop(f)`,
  `create_pop()`, `pop_is_valid(id)`. Verbose, but uniform and easy to grep.
- **Relationships** as first-class objects: unique, many and unindexed links; a choice of
  index storage (list, array, std_vector); composite keys; back-references maintained
  automatically.
- **Serialization** with schema evolution: tag-based selective save and load, tolerant of
  version changes, generated rather than hand-written.
- **The `ve` SIMD library**: `fp_vector`, `int_vector`, `mask_vector` and
  `tagged_vector<id>`, run through `ve::serial/serial_unaligned/par_*::execute<tag>(count,
  fn)`, where `par_*` splits the work into chunks over TBB or PPL. x86-64 only, with SSE4.2,
  AVX and AVX2: no AVX-512 and no NEON.
- **Aligned, padded buffers.** Property buffers are **64-byte aligned and padded past the
  live count to a multiple of the SIMD width**. Vector loops therefore have no scalar tail,
  and reading or writing lanes past the end is safe. This trick is independent of `ve` and
  worth keeping whatever SIMD library is used. "Safe" is a memory-safety statement only.
  Tail lanes may hold arbitrary values after a kernel runs, so checksums and serialization
  never read past the live count (`design_engine_core.md` §2.3).

### 1.3 Its multithreading contract is weak

dcon's contract says what callers may do at the same time. This design keeps its division of
labour and replaces its rules with stronger ones.

Safe: concurrent reads through `const`, and concurrent writes to disjoint ranges. Unsafe:
concurrent create and delete, resizing while reading, and composite-key lookups during
mutation. There is no internal locking. Parallelism is the caller's structure, not a feature
of the container.

The division of labour carries over: the container stays simple, and the scheduler provides
the discipline. The contract itself does not carry over, because it is only a memory-safety
floor. "Concurrent reads through `const`" is safe against other reads. It is not safe
against a concurrent in-place write to the same column, and a determinism contract has to
forbid that write. §4 and `design_engine_core.md` §4.1 give the stronger rules that replace
it.

### 1.4 What transfers and what doesn't

The table lists each piece of dcon and what this design does with it.

| dcon piece | Verdict for SimEstab |
|---|---|
| SoA, tagged handles, generated accessors | Adopt, with a generational id: the handle's slot is the row, and a per-slot generation tells a new occupant from an old one (§2.2). A dcon handle is the bare index, so a reused slot silently names a different instance |
| Aligned, padded buffer layout | Adopt |
| Relationships (links, composite keys) | Adopt the design. This is the hard 20% to build ([Q32](open_question.md#q32-relationships)) |
| Storage types | Adopt `erasable`'s layout as the one storage model, the **pool** (§2.2): holes stay where instances were erased and nothing moves. Strengthen it three ways: generations make a stale handle detectable, freed slots are reused lowest-first instead of from a LIFO free list, and a slot whose generation runs out is retired. Adopt `contiguous` as `[[=append_only]]` (§2.1). Do not adopt `compactable`: moving a row changes its slot, and so the entity's id. A dense kind behind an id-to-row table is open ([Q69](open_question.md#q69-a-dense-storage-kind)) |
| `size{N}`, `size{expandable}` | Adopt `size{N}` as the cap, which every object type has (§2.1). Do not adopt `expandable`: reserving address space at the cap and committing it as the pool fills keeps every address fixed without allocating up front (§2.2) |
| Property types | `bitfield` is kept ([Q29](open_question.md#q29-how-are-bitfields-made-canonical)). `array{index}{T}`, one column per row of a fixed index type, is open ([Q68](open_question.md#q68-per-index-column-groups)). `vector_pool` is a candidate for relationship storage ([Q32](open_question.md#q32-relationships)). `derived`, `object` and hooks are not adopted; this design's `[[=derived]]` is a different thing, a cache column (§2.1) |
| Serialization with schema evolution | Adopt the design. Savegames are bit-exact fixed-point state |
| External DSL and generator executable | Replace with C++26 reflection (§2) |
| `ve` SIMD library | Replace with C++26 `std::simd` (§3) |
| TBB/PPL `par_*` | Replace with OpenMP or TBB at system level (§4) |
| Float-centric properties | Core properties are fixed-point or integer (`design_engine_core.md` §2.1). Floats appear only in snapshot projections |

## 2. Replacing codegen with C++26 reflection

C++26 reflection replaces dcon's external generator. This section lists the reflection
features the container uses, shows the schema as annotated structs (§2.1), and covers what
reflection leaves to hand design (§2.2).

P2996 was adopted into C++26 at the Sofia 2025 meeting. GCC 16 ships it behind `-std=c++26
-freflection`, including annotations (P3394), expansion statements (`template for`) and
`define_static_{string,object,array}`. The container's GCC 16.1 compiles and runs every
primitive the generator needs:

| Primitive | Purpose here | GCC 16.1 |
|---|---|---|
| `^^T`, splices, `std::meta` queries | walk descriptor structs | ✅ |
| `nonstatic_data_members_of` + `template for` | iterate over properties at compile time | ✅ |
| `std::meta::define_aggregate` | synthesize the SoA struct (one column per property) | ✅ |
| annotations `[[=...]]` + `annotations_of` | per-property metadata (saved, gpu, indexed, …) | ✅ |
| `define_static_string/array` | generated names, GLSL source, binding tables | ✅ |

### 2.1 Schema = annotated C++ structs

The schema is a set of ordinary C++ structs, one per object type, kept next to the
simulation code. Annotations on the members say what each property takes part in. The dcon
DSL becomes:

```cpp
// no [[=cap]]: pop gets the default cap of 2²⁴ (§2.2)
struct pop {                          // descriptor only — never instantiated as AoS
    [[=saved]] [[=viz]] fx32   wealth;     // fixed-point (engine core §2.1)
    [[=saved]]          fx32   literacy;
    [[=saved]]          int32_t size;
};
```

This list is the single definition of the annotations. `cap` and `append_only` annotate the
object type; the others annotate members. Every annotation is optional:

- `[[=cap(N)]]`: sets the object type's **cap**, the most entities of this type alive at one
  time. Every object type has a cap. Without this annotation it is 2²⁴ (16,777,216). N may be
  1 to 2³²−1, because a slot is a `u32` (§2.2). `EngineConfig.entity_capacity` sets or
  overrides it per type. The cap is closed at the freeze and joins session identity. Memory
  is reserved at the cap and committed as the pool fills, so a large cap costs address
  space, not memory (§2.2). A cap below the default states a bound on purpose, such as a scenario with a fixed
  settlement limit. What a create at the cap does depends on the kind of cap, a game rule or
  a ceiling (§2.2; [Q31](open_question.md#q31-what-does-hitting-a-declared-cap-do)).
- `[[=append_only]]`: the object type has no erase, and the generator emits no erase API for
  it. Every slot below the extent is live and every generation is 1, so scans over it need
  no live mask (§2.2). It suits types that only grow, or never change after loading, such as
  provinces. It is dcon's `contiguous` storage.
- `[[=saved]]`: serialized into savegames.
- `[[=viz]]`: included in the snapshot projection (§5.1).
- `[[=gpu]]`: a subset of `viz`. The column is also staged to a storage buffer, with
  generated GLSL declarations and bindings (§5). It carries no stage information, so every
  `[[=gpu]]` destination buffer is created with the union of the read usages (§5). A
  per-stage refinement (`[[=gpu(compute)]]`) is future work and purely additive.
- `[[=derived]]`: the column is a cache that systems rebuild from other state. It is not
  saved, and it is rebuilt after load. It is left out of the tick digest and the rolling
  checksum. The full checksum rebuilds it and compares (`design_engine_core.md` §2.3), which
  catches a cache that drifted from its source. A cache that is not declared `derived` is
  state: it is saved and hashed like any other column.

**Every object type has ids.** An id is a slot and its generation (§2.2), not a stored
column, so no annotation declares it. A save holds every slot's generation, so ids survive a
save and load (§2.2). Publish synthesizes the id column for an engine view that projects it (§5.1).
The id passes through the projection unconverted: the `fixed<> → float` mapping does not
apply to it. It is not eligible for `[[=gpu]]`, because 64-bit integers in GLSL need an
extension. Its two `u32` halves could be projected instead (§5). Python sees `uint64`.

A `consteval` block walks the descriptor and calls `define_aggregate` to create the real
container type. This shape was verified to work:

```cpp
consteval {
    std::vector<std::meta::info> cols;
    for (auto m : nonstatic_data_members_of(^^pop, access_context::unchecked()))
        cols.push_back(data_member_spec(
            substitute(^^column, {type_of(m)}),      // column<T> = aligned+padded buffer
            {.name = identifier_of(m)}));
    define_aggregate(^^pop_soa, cols);
}
```

Everything dcon generates from the DSL becomes reflection-driven library code, stamped out
from the same descriptors: typed id types, accessors, `for_each`, serialization, checksum
visitors (`design_engine_core.md` §2.3) and the snapshot projection. Schema and simulation
code cannot drift apart, because there is no second source of truth.

GCC API notes from the verification. The profiles pin the compiler version, and the build
sets `-freflection` (see the top of this document).

- `annotations_of(m)` takes one argument. Filter by `dealias(remove_cv(type_of(a))) ==
  ^^tag_t`. `remove_cv` and `dealias` need explicit `std::meta::` qualification (§8).
- Annotation queries must run in a constant-evaluated context, so wrap them in `consteval`
  helpers. `template for` over members needs `define_static_array(...)`.
- Type splices in expression position need `typename [: r :]`.

### 2.2 What reflection does *not* solve

Reflection stamps out structure; it does not design semantics. This section covers what is
still designed by hand: relationships, the pool that stores every object type, identity,
creates and erases, caps, the order rows are visited in, and what a save holds.

- **Relationships**: link storage, indexing strategy, composite keys and fix-up at delete.
  Start with the two cases the simulation needs, unique links and many-links stored as
  arrays, rather than porting dcon's full matrix. It is not yet designed
  ([Q32](open_question.md#q32-relationships)). The pool below fixes four constraints on it:

  - A link stores the target's slot. Its width follows the target type's cap: `u16` when the
    cap is at most 2¹⁶−1, `u32` above.
  - An erase fixes every link into the erased entity, by the relationship's delete rule, in
    the terminal commit, before any create can reuse the slot.
  - Links to entities that survive never change, because rows never move.
  - A list of the links into one entity (a reverse index) is kept in slot order, or rebuilt
    in slot order. Its order must follow from state, never from the order links were made.

- **Every object type is stored as a pool.** There is one storage model, not a choice per
  type. A pool holds:

  | Part | What it is |
  |---|---|
  | columns | one per property, indexed by slot, with address space reserved for the cap |
  | live bitmap | one bit per slot, set while the slot holds an entity |
  | generation column | one `u32` per slot, the slot's reuse counter (below) |
  | retired bitmap | one bit per slot, set when the slot may never be used again |
  | chunk live counts | one count per chunk (§4), so a scan skips empty chunks |
  | extent | one past the highest slot ever used; scans cover `[0, extent)` |

  **Rows never move.** An entity's slot is its row for its whole life. An erase leaves a
  hole, and a later create may fill it. This is OpenTTD's pool, and dcon's `erasable` storage
  with three changes: generations, reuse of the lowest free slot, and retirement (below).

- **An id is a slot plus a generation.** `id = slot << 32 | generation`, a `uint64`, tagged
  per object type (`pop_id`).

  - Every generation starts at 1, so id 0 is never issued and serves as null.
  - An erase adds one to the slot's generation, so the next entity in that slot gets a
    different id.
  - **Lookup is O(1).** The id's high half is the row. The entity is alive only if the row is
    below the extent, its live bit is set, and its generation equals the id's low half. The id
    is computed from the slot and the generation column, so no id column is stored.
  - **No id value is issued twice.** When an erase would take a generation past 2³²−1, the
    slot is **retired**: it is never free again and never live. A slot is reused at most once
    per tick, so retirement takes 2³² ticks of churn on one slot, 4.5 years at 30 Hz. It
    costs one slot. EnTT, flecs, bevy and slotmap let the generation wrap instead, which lets
    a stale id name a new entity.
  - **Id order is slot order**, because the slot is the id's high half. Sorting ids never
    depends on how often slots were reused.

  Inside a tick, systems address rows directly: `column[row]` is the whole access path. A row
  stays valid for its entity's whole life, but a bare row cannot tell that entity from a later
  occupant of the slot. So **a row never crosses a boundary**: not into a command, a snapshot
  reader, a savegame, a replay, or anything a mod keeps past the tick. Ids cross every
  boundary.

- **Creates and erases happen in the terminal commit.** Structural change is confined to the
  terminal commit (`design_engine_core.md` §4.1). The commit runs two steps, in this order:

  1. **Erases.** Staged erases form a set: erasing one entity twice in a tick is one erase.
     For each, the commit clears the live bit, adds one to the generation (or retires the
     slot), zeroes the row, and fixes the links into it. Zeroing means a dead lane never
     feeds a fault path, such as a fixed-point division by zero (§3).
  2. **Creates.** Staged create buffers merge in fixed task order (`design_engine_core.md`
     §4.1). Each accepted create takes the lowest free slot and writes every column. A slot
     freed in step 1 is free in step 2.

  The commit costs O(erases + creates + links into erased entities). No step is O(rows).

  **The lowest free slot comes from the bitmaps, not from a free list.** A free slot is below
  the cap and is neither live nor retired. The search starts at a `first_free` hint and reads
  the bitmaps a word at a time. The choice is a pure function of the bitmaps, which are saved
  state. So every machine picks the same slot, and a loaded session picks the same slot as
  one that never saved. A LIFO free list, which EnTT, flecs, bevy and dcon use, is
  deterministic only if the list itself is saved exactly. Lowest-first also keeps live rows
  packed toward low slots, which keeps scans short.

  **The extent never shrinks during a session.** A create above the extent raises it. If the
  extent shrank, the slots above it would lose their generations, and a later entity there
  could be issued an id already used. The data pages of a fully empty chunk may be
  decommitted, because a create writes every column. The generation column is never
  decommitted.

- **Every object type has a cap**: the most entities of the type alive at one instant
  (§2.1). It is 2²⁴ unless declared, and at most 2³²−1, because a slot is a `u32`. It does not
  bound creation over time: no id is issued twice, so a session may create and erase without
  limit.

  - **Memory is reserved at the cap and committed as the pool fills.** At the freeze, the
    engine reserves address space for `cap × element size` for every column
    (`design_engine_core.md` §2.4 step 2). It commits pages as the extent reaches them.
    Addresses never change for the whole session. A 2²⁴ cap of 8-byte values reserves
    128 MiB of address space per column. A thousand such columns use about 125 GiB of the
    128 TiB a 64-bit Linux process can address.
  - **Commit failure ends the session; it is never a rejection.** The terminal commit commits
    the pages it needs before it changes anything. A failure therefore leaves core state
    whole at tick N, and the tick is abandoned rather than half-applied. The freeze uses the
    same order, fallible steps before observable ones (`design_engine_core.md` §2.4). The
    engine logs `critical` and enters `failed` (`design_python_api.md` §2), as it does on GPU
    device loss (`design_engine_core.md` §5). It must not fall back to rejecting the creates
    that did not fit. That would make the accepted set depend on machine memory, so two
    machines replaying one command stream would diverge by how much RAM they had. A bound
    that affects outcomes has to be the cap: identical on every machine and recorded in the
    replay header. On Linux, overcommit can let a commit succeed and fail later, when a page
    is first touched. So the engine commits explicitly and counts committed bytes against a
    budget.

  **A create at the cap is refused.** Three rules make that deterministic rather than merely
  bounded:

  - **The check runs after the erases.** Erases staged this tick free their slots in step 1,
    so the free count is `cap − live − retired` after step 1. A tick that erases 100 and
    creates 100 in a full pool succeeds. Checking first would reject it for no reason.
  - **Merge order fixes which creates win.** Staged create buffers merge in fixed task order
    (`design_engine_core.md` §4.1), and the first that fit are accepted. They take ascending
    free slots in the same order. Otherwise the accepted *set* would depend on task
    scheduling: a desync disguised as a resource limit.
  - **The refusal is reported, and how depends on the kind of cap.** A game-rule cap
    reports; a ceiling stops (the two kinds are below). A create requested by a command
    reports through that command's own outcome (`design_python_api.md` §7.1), which goes
    back to a caller that still exists. A create with no command behind it, a system
    creating on its own, has no caller to return to. It emits one reliable-class event per
    `(object type, requesting source, tick)`, carrying the count. It does not emit one event
    per rejected create, since nothing bounds that volume. The two kinds of cap below keep
    this path bounded.

  Every cap is closed at the freeze and joins session identity (`design_engine_core.md`
  §2.3). So a replay against a different cap is rejected by the replay header rather than
  diverging. That is correct, because rejection behaviour depends on the number.

  **There are two kinds of cap, because a cap can mean two unrelated things.** "At most 200
  settlements, by design" and "no more than 10⁶ particles, or something has gone wrong" are
  different statements. Treating them alike leaves the create-at-cap question without an
  answer: one is ordinary play and the other is a bug.

  | The cap is | Reaching it means | Behaviour |
  |---|---|---|
  | **a game rule**: "at most N of these ever exist" | normal play, every session | deterministic rejection, reported as above: one coalesced record per `(type, source, tick)`, or the command's outcome |
  | **a ceiling**: a bound nobody expects to reach | a runaway system, or a cap set wrong | an error: stop and report, loudly |

  **The ceiling reading is the default.** A cap meant as a game rule has to say so on the
  type. A system creating past a ceiling is a bug and should look like one. A limit that
  silently absorbs a runaway loop hides it. The default cap of 2²⁴ is a ceiling: at 64 bytes
  per row it stops a runaway system at 1 GiB, long before memory runs out.

  Both kinds stay deterministic, which is why stopping is a safe response and not a new
  desync source. The cap is part of session identity and merge order is fixed, so **every
  machine reaches the cap on the same create**. Every instance therefore stops at the same
  point. It is not a local reaction to local pressure.

  **Whose error it is decides the response**, by the usual attribution rule
  (`design_modding.md` §5.2). An engine system past a ceiling stops the simulation. A mod's
  system past a ceiling suspends that mod and reports (`design_modding.md` §4.2). How a
  declaration says which kind of cap it is, what "stop" means, and what suspending a Tier 3
  mod means are open ([Q31](open_question.md#q31-what-does-hitting-a-declared-cap-do)).

  One interaction constrains how a cap may be declared. Mods cannot read a cap or the
  committed memory (below), so a mod cannot check before creating. For mods, a ceiling
  must therefore be reachable only by a truly runaway system, never by ordinary play. A cap
  that a mod's normal behaviour can reach is a game rule, and must be declared as one.

  **Mods cannot read the cap or the committed memory.** The C ABI omits both (§7.3), so
  pool fullness never becomes an input to mod logic. A mod learns only that a create was
  refused, and only when a cap is reached.

- **Rows are visited in slot order.** Slot order is also id order (above). The order
  follows from the live bitmap, which is saved state, so a loaded session visits rows in the
  same order as one that never saved. It depends on the history of creates and erases, so
  nothing may treat it as creation (age) order. Stagger schedules ("update a tenth of the
  pops each tick") and RNG counters key on the id, never on the bare row. A new occupant then
  never inherits the schedule or random stream of the entity it replaced.

  Scans run over the chunks of `[0, extent)` and skip a chunk whose live count is 0. Inside a
  chunk, rows are masked by the live bitmap. A per-row update may compute on dead lanes,
  because nothing reads them. A reduction, a staged write, a create or an event must mask
  them. An append-only type (§2.1) has no dead lanes and needs no mask.

- **A save holds the layout, not just the entities.** For each object type it holds the
  extent, the live and retired bitmaps, the generation column for every slot below the
  extent, and the saved columns of live rows. Dead slots keep their generations, so a stale
  id stays stale after a load. Load puts every entity back in its slot, and derived columns
  (§2.1) are rebuilt. A loaded session therefore continues exactly as one that never saved,
  and no peer has to reload a save to agree with another.

- **Overflow and rounding policy** of the `fixed<>` columns belongs to the `fixed` type
  (`design_engine_core.md` §2.1), not to the container.

## 3. SIMD integration

The container uses C++26 `std::simd` instead of dcon's `ve`, and keeps dcon's layout ideas.
This section defines the column buffer and its padding rule, and the rules for gather and
scatter.

`std::simd` is present and works in the container's libstdc++ 16 (`<simd>`, namespace
`std::simd`, `std::simd::vec<T>`). The native float width is 8 under `-march=x86-64-v3`,
which is the build's default ISA baseline, set by `LIBSIM_ESTAB__ARCH_BASELINE`. This
answers the note on libstdc++ coverage in `design_engine_core.md` §4.4: the coverage is
there. Highway remains the fallback if gaps in `std::simd` appear in practice, for example
missing gather/scatter or fixed-point multiply-high patterns. Whether `std::simd` is enough
is open ([Q30](open_question.md#q30-is-stdsimd-enough)).

Design points:

- **`column<T>` buffer type.** It is 64-byte aligned, with the element count padded up to a
  multiple of `64 / sizeof(T)`: one cache line of elements. The padding is therefore **per
  column element type, never one figure for the table**. Buffers are zero-initialized
  (`design_engine_core.md` §2.2, determinism). Loops have no scalar tail. Padding lanes are
  masked out only where their values could mix with live state, as in reductions.

  Canonical consumers, the checksum and serialization visitors, iterate over state only.
  That is the columns of live slots, plus the generation column and bitmaps below the extent
  (§2.2), with no dead rows, no padding, no spare allocation, no tail lanes, and fixed
  little-endian output (`design_engine_core.md` §2.3). Zero-initialization, and zeroing a row
  at erase (§2.2), are hygiene. They do not make it acceptable to hash raw buffers.

  **Buffer padding and chunk size are different quantities.** This bullet is about the space
  allocated past the live count (dcon's tail-free trick, §1.2). The chunk is the unit of
  subdivision, defined once in §4 and not restated.

  **Why the rule is per element type, and why it is stated in bytes.** Lane count depends on
  `T`, not on the table. Measured with the container's toolchain under `-march=x86-64-v3`,
  `std::simd::vec<int32_t>` has 8 lanes and `std::simd::vec<int64_t>` has 4. A single figure
  for the table, such as 8, is the `int32` answer applied to every type. It is wrong in two
  directions, and only one of them merely wastes memory:

  | Direction | Consequence |
  |---|---|
  | too small for narrow types | An `int8` column padded to 8 elements is not a whole number of 32-lane vectors, so the tail-free guarantee, which is the purpose of the padding, fails for it. This is a correctness defect, not a tuning one |
  | too large for wide types | Q32.32 world coordinates are `int64`, where 4 would do. The core's most common column type is the one a single figure over-pads |

  Padding to `64 / sizeof(T)` elements is the same as padding the byte size to a multiple of
  64. That one rule meets three requirements, which is why it is stated in bytes rather than
  lanes:

  - **No tail at any ISA baseline.** 64 bytes is one AVX-512 vector, two AVX2 vectors or
    four SSE vectors. A column padded this way is a whole number of vectors for every `T`
    and every ISA level. So `LIBSIM_ESTAB__ARCH_BASELINE` can change without a new padding
    rule. That matters because it is a build option (§3), not a constant.
  - **Bounded allocation, independent of type.** The waste is at most 63 bytes per column,
    whatever `T` is. The cautious uniform alternative pads every column to the widest lane
    count any type reaches, 32 under this baseline. That would leave an `int64` column with
    up to 248 bytes of slack for the same guarantee, and gain nothing.
  - **No false sharing when columns share an allocation.** Each column's extent is a whole
    number of cache lines. The next column starts 64-byte aligned with no filler between
    columns, and no two columns' live data share a line (§4, `design_engine_core.md` §4.3).

  The chunk quantum needs no separate rule. 1024 elements (§4) is a multiple of `64 /
  sizeof(T)` for every `T` up to 8 bytes, so chunk boundaries always fall on column-padding
  boundaries. A future `T` wider than 8 bytes would be the first case to check.
- **Core columns are integer or fixed-point.** Integer SIMD is bit-exact across ISAs and
  lane widths, so runtime dispatch is safe (`design_engine_core.md` §4.4). Qm.n multiplies
  need widen, shift and narrow kernels. These live in the SIMD layer of `fixed<>`; the
  container only guarantees layout.
- **Tagged gather and scatter.** Relationship traversal reimplements dcon's `tagged_vector`
  idea on top of `std::simd`: indirect loads through a vector of rows. dcon's rule,
  "scatter with duplicate indices is UB", needs a sharper replacement than "the scheduler
  guarantees disjointness". The scheduler guarantees disjointness across task ranges. It
  says nothing about duplicates within one index vector. A scatter whose vector repeats a
  row has an unspecified winner among its lanes. Its result can then change with lane width
  or code generation, even single-threaded, inside a commit, with every scheduling guarantee
  intact.

  **The rule is about where the indices come from.** A scatter is legal only when its index
  vector has no duplicates *within the vector* and every index lies inside the invocation's
  write span. The absence of duplicates must follow from where the indices came from:
  traversal of a `unique` link, or the distinct rows of the task range. It must never
  rest on an assumption about the data. Many-to-one accumulation therefore never scatters.
  It uses per-task accumulators merged in fixed order, or a sort by destination plus a
  segmented reduction (`design_engine_core.md` §4.3: collect all claims, then resolve them
  in a deterministic pass). Debug builds assert both uniqueness and span containment.

  This is not a new rule. A scatter whose result depends on which lane wins *is* an
  operation that depends on lane width, which the next bullet and `design_engine_core.md`
  §4.4 already forbid. Also, writes whose destination is found at run time already require
  `write_staged` (`design_engine_core.md` §4.1). So an in-place scatter is always confined
  to the invocation's own write span.
- **Lane-width independence.** Per-element operations and wrapping reductions do not depend
  on order. Anything sequential must follow a fixed logical order (`design_engine_core.md`
  §4.4).

## 4. CPU parallelism (OpenMP / TBB)

The container provides shapes that make parallel phases easy; the scheduler provides the
rules. This section defines the chunk and says how systems run in parallel over chunks.

dcon's contract (concurrent reads, disjoint writes, no structural change; §1.3) is a
**memory-safety floor, not the determinism contract**. Its read clause is the part that does
not carry over. An unscoped read of a column that another task writes in place is a data
race, and its result depends on the schedule. dcon can leave that to the caller because it
does not manage parallelism at all. Here the scheduler manages it, and its rules are
strictly stronger: per-column access declarations and the phase invariant of
`design_engine_core.md` §4.1. The container still needs no internal locking, only these
shapes:

- **Chunked columns.** **The chunk quantum is defined here and nowhere else.** It is counted
  in *elements* and is a build constant, `LIBSIM_ESTAB__CHUNK_ELEMENTS`, next to
  `LIBSIM_ESTAB__ARCH_BASELINE`. It is a power of two, and at least `64 / sizeof(T)` for the
  narrowest column type in use. That is the same per-type quantity §3 pads to, and it is 64
  for a 1-byte column. It is sized up so that one chunk of a 4-byte column is about one
  page: default 1024. As a power of two ≥ 64, the default meets the constraint for every `T`
  up to 8 bytes at once. So chunk boundaries always coincide with column-padding boundaries,
  and no chunk starts mid-vector. Retuning is a rebuild, not a design change.

  The constant is built. It is a CMake cache variable, validated at configure time, and it
  reaches code as `sim_estab::core::limits::chunk_elements`. The same three constraints are
  checked again as `static_assert`s (`design_limits.md` §3).

  Each chunk keeps a count of its live slots. A scan skips a chunk whose count is 0, and the
  terminal commit updates the count of every chunk it touches (§2.2).

  A chunk is a fixed range of slots and has no spatial meaning. It is the unit of
  parallel-for work items, SIMD iteration and false-sharing isolation
  (`design_engine_core.md` §4.3), and nothing else. The vocabulary, chunk versus task range
  and why neither is called a "partition", is in `design_engine_core.md` §4. Chunks are not
  a GPU unit: uploads are whole-column (§5), so no workgroup size constrains this number.
- **Parallel-for over chunks, at system level**, not built into the container:
  - **OpenMP** is verified working (`gcc-16 -fopenmp`, 8 threads in the container). It has
    the least friction. `#pragma omp parallel for` over chunk indices with a static schedule
    is deterministic in *work assignment*, and commit order stays fixed by chunk index.
  - **TBB** (Conan `onetbb`, not a dependency) is worth it only if the engine later wants
    task graphs, nested parallelism or one scheduler for all subsystems. It is not needed to
    start.
  - Either way, **work items and commit order are fixed by chunk index**. Work stealing may
    reorder execution, never results (`design_engine_core.md` §4.3).
- **Access declarations from annotations.** A system declares an access kind per column:
  `read_full`, `read_local`, `write_local`, `write_staged` or `write_dbl`
  (`design_engine_core.md` §4.1). Reflection turns each declaration into a const or mutable
  span of exactly the permitted extent, so the span a system holds *is* its permission. The
  phase invariant can then be checked statically, and the scheduler derives the phase cuts
  once (`design_engine_core.md` §4.1, §4.5).
- **Phase stability.** While any phase of the tick runs, the container makes no structural
  change. The live set, the extent and every generation are fixed, so a row cannot change
  occupant mid-tick. This makes the read-span rule provable, not just intended. Rows never
  move at all (§2.2).
- **Structural changes** (create, delete, relationship rewiring) happen only in that
  terminal commit, through thread-local staged buffers merged in fixed order. So the
  practices dcon lists as "definitely bad ideas" cannot occur. The commit costs
  O(erases + creates + links into erased entities) and runs sequentially (§2.2).

## 5. GPU / compute-shader integration

The GPU path carries snapshots, never core state. This section fixes the backend, maps
columns to storage buffers, specifies the upload path against SDL3's contract, and states
the limits of that path.

dcon has nothing here, and this is where reflection pays off a second time. The constraint
comes from `design_engine_core.md` §5: **GPU compute is peripheral-domain only**. The
container's GPU work is about *snapshots*, not core state.

**Backend scope.** The GPU path targets SDL3's Vulkan backend only, with SPIR-V from
glslang, which is already present. D3D12 and Metal need DXIL and MSL, which glslang does not
emit. Supporting them means adding SDL_shadercross, and that is future work. Linux and
Windows are covered, since both have Vulkan. macOS has no GPU path. The device must
therefore advertise SPIR-V only. That makes SDL's backend choice deterministic (Vulkan, or
device creation fails), instead of picking a backend whose shader format the engine cannot
produce.

Everything below is written against the vendored `SDL3/SDL_gpu.h`, not against the general
std430 and persistent-mapping idiom. Where SDL's contract differs from that idiom, SDL wins.

- **SoA columns map one-to-one onto storage buffers**: `std430`, scalar stride, **measured,
  not assumed**. The `[[=gpu]]` subset of the snapshot projection (§2.1) is a set of tightly
  packed scalar arrays, which is what a storage buffer wants. SDL confuses this. It requires
  storage-buffer data to "respect std140 layout conventions" (`SDL_gpu.h:976-978`,
  `:2850-2852`), and narrows that in the same sentence to "vec3 and vec4 fields are 16-byte
  aligned". Strict std140 would give a scalar array a 16-byte element stride: 4× the memory
  and bandwidth. A mismatch would also fail silently: the shader would read at the wrong
  stride and render garbage, with no error.

  **A spike settled it.** A compute shader wrote `i + 1` into element `i` of a
  `layout(std430)` buffer, over a destination filled with `0xCD`. The result was read back
  and inspected byte by byte, with a `layout(std140)` shader as a positive control. Results
  were identical on two independent Vulkan drivers (Intel Mesa ANV and lavapipe), with SDL
  debug mode on:

  | Shader declares | SPIR-V `ArrayStride` | Observed |
  |---|---|---|
  | `std430` | 4 | `01 02 03 04 …`: 1:1, stride 4 |
  | `std140` (control) | 16 | `01 cdcdcdcd cdcdcdcd cdcdcdcd 02 …`: stride 16 |

  The control reproduces stride 16, with the sentinel visible in the padding, so the
  positive result can be trusted. **Conclusion: a scalar column is uploaded unmodified and
  read at a 4-byte stride.** SDL's std140 note is caution for the D3D12 and Metal backends,
  which this design does not target.

  **The accessor indirection stays anyway.** The generator emits a per-column accessor on
  both sides: `col_get(i)` / `col_set(i, v)` in C++, and the matching function in the
  generated GLSL preamble. Every reader and writer goes through it. Today every body is
  `buf[i]`. The indirection costs nothing. It leaves one place to change if a future D3D12
  or Metal port needs quad-packing: four scalars per 16-byte element, `buf[i >> 2][i & 3]`,
  with no padding and no repacking. A `[[=gpu]]` column of 4-byte scalars is padded to a
  multiple of `64 / 4` = 16 elements (§3), and so to a multiple of 4. That fallback would
  therefore need no extra padding rule. The same holds for any scalar width, because padding
  to 64 bytes is always a multiple of a 16-byte quad.

  **This assumption must stay tested.** A driver or SDL change that silently changed the
  stride would corrupt every rendered frame with no error. So the spike belongs in the GPU
  test executable (`libsim_estab_viz_test`) as a regression test, not in a scratch
  directory. It is not yet ported (see `TODO.md`).

- **GLSL is generated from the same descriptors.** Reflection emits the storage-buffer
  declarations, the accessor preamble and a matching C++ binding table
  (`define_static_string`), compiled at runtime by glslang. The CPU and GPU sides of the
  schema cannot drift apart.

  **Binding indices are not free to choose.** SDL fixes the descriptor set by shader stage
  and access mode (`SDL_gpu.h:2590-2606` compute, `:2695-2730` graphics):

  - compute uses set 0 for read-only storage buffers (after sampled and read-only storage
    textures), set 1 for read-write storage buffers, and set 2 for uniforms;
  - graphics uses sets 0 and 1 for vertex, and 2 and 3 for fragment;
  - the order *within* a set is fixed by resource category.

  So the generated table is keyed on (stage, access mode, category) and emits `layout(set =
  S, binding = N)`, never a bare `binding = N`.
- **Usage flags are fixed when a buffer is created** (`SDL_gpu.h:987-991`), before any
  shader runs, and `[[=gpu]]` carries no stage information (§2.1). So every `[[=gpu]]`
  destination buffer is created with the union `GRAPHICS_STORAGE_READ |
  COMPUTE_STORAGE_READ`. Columns that a compute peripheral *writes* are not `[[=gpu]]`
  snapshot columns at all. They live in the peripheral's own instances (§5.1).
- **Fixed-point converts to float once, at the projection boundary**
  (`design_engine_core.md` §5). The snapshot publisher converts `fixed<>` columns to float
  arrays while projecting into an engine view's block (`design_engine_core.md` §3.1). GPU-side
  compute (viz, analytics, neural-net inference) reads the storage-buffer snapshot, and can
  affect the core only through commands.

**Upload path (v1).** This is the CPU/GPU lifetime boundary of `design_engine_core.md` §3.1,
written against SDL's actual contract:

1. **Lifetime boundary.** The GPU never reads engine view memory. The reader (a renderer or a
   GPU-compute peripheral) copies the columns it needs, on the CPU, into a staging transfer
   buffer. That CPU copy is the boundary. The engine view block it copied from stays the reader's
   until its next `take()`.
2. **Staging is mapped per frame, never persistently.** SDL requires that "you must unmap
   the transfer buffer before encoding upload commands" (`SDL_gpu.h:3837`). So a
   persistently mapped upload ring cannot be built on this backend. The sequence is
   `SDL_MapGPUTransferBuffer(staging, cycle = true)`, then a `memcpy` of every `[[=gpu]]`
   column, then `SDL_UnmapGPUTransferBuffer`, then encode. There is one staging buffer per
   frame, sized to the sum of the `[[=gpu]]` column sizes. That sum is the render engine view's
   declared projection spec (`design_engine_core.md` §3.1) times the engine view's maximum rows
   (§5.1), so the size is known at the freeze rather than discovered. `cycle = true` on the map makes reuse across frames safe
   without hand-written fence tracking of the staging buffer.
3. **Destinations are cycled and rewritten whole.** There is one `SDL_UploadToGPUBuffer` per
   column, with `cycle = true` and a region covering the entire destination buffer. Cycling
   makes all contents undefined: "when cycling, all data in the resource is considered to be
   undefined for subsequent commands until that data is written again"
   (`SDL_gpu.h:341-343`). Hence the governing invariant:

   > **Every cycle of a destination buffer is accompanied by a write of that buffer in
   > its entirety, within the same copy pass.**

   Two rules follow:
   - **One destination buffer per column.** If several columns were in one buffer, cycling
     it for the first column's write would make the others undefined.
   - **No partial upload.** Every upload writes the whole column. Partial upload does not
     work with cycling and is not part of this design (see below).

   The invariant also covers SDL's "the contents of this buffer are undefined until data is
   written" (`SDL_gpu.h:2844`): a whole-buffer first write needs no separate initialization
   rule.
4. **Versioning.** Each destination keeps one scalar, `last_uploaded_snapshot_tick`. It is
   used only to skip the upload when the published tick has not advanced, which is the
   normal case when rendering at 60 fps over 30 Hz ticks. It advances **when the
   submission's fence signals**, never when commands are recorded.
   `SDL_CancelGPUCommandBuffer` executes none of the queued commands
   (`SDL_gpu.h:4387-4390`), and the ordinary no-swapchain-texture path reaches it
   (`design_patterns.md` §6). A cursor advanced at record time would then leave the
   destination holding older bytes permanently while claiming to be current. Between submit
   and fence signal the cursor still holds the previous tick, so one tick may be uploaded up
   to `frames_in_flight` times. That is bounded and harmless.
5. **Presentation is gated on fences.** Only uploads whose fence has completed are presented
   or read. GPU completion is never inferred from "same snapshot tick as last frame".

**Cost, and the metric to watch.** Whole-column upload pays `sum(bytes of [[=gpu]] columns)`
per upload. Uploads are skipped while the published tick has not advanced (step 4). Normally
there is one upload per published tick: at most 30 per second at the default 30 Hz tick
rate. While a fence is pending, a tick can be uploaded again (step 4), but never more than
once per frame, so at 60 fps the worst case is 60 uploads per second. The example rates
below assume that worst case; at one upload per tick they halve. At 10⁵ entities × 8 float
columns, one upload is about 3 MB, or about 190 MB/s at 60 per second, which is
unremarkable. At 10⁶ × 16 it is about 64 MB per upload, or about 3.8 GB/s, which is not
viable. So upload bytes per frame is published alongside the engine view metrics of
`design_engine_core.md` §3.1: publish duration, publish bytes per second, matched rows, last
published tick and consumer lag. Reaching GB/s rates is the trigger for revisiting the
approach.

These figures illustrate the cost model; they are not a budget. There is no cap on projected
row width, by decision (`design_engine_core.md` §3.1, `design_limits.md` §5), because width
× matched rows is what matters, and matched rows are bounded only by the cap.

**GPU buffers are sized from the engine view, not the table.** An SDL GPU buffer cannot be resized
after creation (`SDL_gpu.h:987-991`: usage and size are fixed at create). Every object type
has a cap (§2.2), so a destination could be sized once, at the cap. But a cap is a ceiling on
live entities, not a working size, and sizing every `[[=gpu]]` column at 2²⁴ rows would
reserve device memory nobody uses. So each destination is sized from its engine view's maximum rows
(§5.1): the most rows one publish of that engine view can hold.

How an engine view declares its maximum, what the default is, and whether destinations suballocate
from a few large buffers are open (`design_limits.md` §7;
[Q39](open_question.md#q39-the-gpu-allocator-for-growing-worlds)). Suballocation would let
one destination hold several columns without breaking the cycling invariant, because cycling
would move to the allocation rather than the column. Every candidate must meet one fixed
constraint: **a destination is written in its entirety within the copy pass that cycles
it**, whatever the allocation underneath.

The GB/s figure above is only this document's trigger for revisiting whole-column upload. It
is not the publish threshold. The two answer different questions: device bandwidth here, and
the sim thread's projection cost in `design_limits.md` §5. Publish uses its own
`projection_warn_bytes_per_second`, per engine view.

The 10⁶ case above also shows what a large world needs. Reaching 10⁷ live rows is not a
matter of narrower columns: a 32-byte projection is still 320 MB per publish. It needs the
projection to stop being *every live row*, since no reader wants every live row at that
scale. **An engine view declares both projection axes.** Over columns it declares its spec. Over
rows it declares a predicate kind whose parameters arrive with each publish
(`design_engine_core.md` §3.1, §3.4). §5.1's generator emits both. The row half costs it
little: evaluating the predicate gives a mask, which is ANDed with the live bitmap, and
everything after the mask is the publish scan and gather (§5.1). What is still open is where the
predicate scan is charged, on the sim thread or the worker pool (`design_limits.md` §7;
[Q35](open_question.md#q35-where-is-the-predicate-scan-charged)), and what row width the
scan assumes ([Q61](open_question.md#q61-what-row-width-does-the-predicate-scan-assume)).

**Partial upload and partial publish are both out of scope**, not just for v1. Re-uploading
or re-copying only the chunks that changed ("dirty" upload, dirty-copy publish) would need
three changes together:

- explicit N-buffering per destination instead of cycling, since a partly written cycled
  buffer is undefined in every chunk not written this frame;
- a per-chunk change stamp kept by the core and *projected into the snapshot instance*.
  Every publish rewrites its whole block, so a stamp meaning "written during this publish"
  would read as "everything is new";
- a projection that keeps core slots, holes included. A snapshot is dense (§5.1), so an
  erase or create shifts every later snapshot row, and change tracking per snapshot chunk is
  invalidated on any tick that erases or creates. Core rows never move (§2.2), so such a
  projection is possible, but it ships dead rows to every reader.

Together these replace the upload contract rather than extend it, which is why this is not a
deferred increment.

**The row predicate does not reopen this.** It is a different axis. A predicate selects
which rows a publish *contains*. Every publish still writes its whole destination, carries
nothing over from the previous one, leaves no chunk unwritten, and reads no change stamp.
None of the three objections applies to it, and none of them is weakened by it.

**Dispatch count.** Dispatch `ceil(count / workgroup_size)` groups, pass the live `count` as
a uniform, and guard on bounds in the shader (`if (i >= count) return;`). Rows `[0, count)`
of a snapshot are all live, because publish gathers only live rows (§5.1), so no validity
test is needed. The bounds
guard exists because padding lanes hold arbitrary values after a kernel runs (§1.2). Never
dispatch over a padded count in the hope that the padding is harmless.

**No GPU-side state may be keyed on a snapshot row across frames.** A snapshot is dense
(§5.1), so an erase or create shifts every later row. Row 7 next frame may be a different
entity, with no sign of the change. So the GPU can address snapshot rows *within* a frame
and no further. This is safe only because every destination is cycled and rewritten whole on
every upload, which discards last frame's row assignment along with its data. The
whole-rewrite invariant serves both purposes, and should not be weakened without revisiting
this rule.

Core slots, unlike snapshot rows, are stable for an entity's whole life (§2.2), and both
halves of an id are `u32`, which GLSL handles natively. So a GPU feature that wants
per-entity state across frames (trails, selection highlight, LOD caches, temporal
accumulation) can key it on slot and generation, if its engine view projects them. Whether and how
engine views project them is open
([Q57](open_question.md#q57-gpu-per-entity-state-across-frames)). Keying such state on a
snapshot row instead is how a renderer starts smearing state across unrelated entities.

**Compute passes are not implicitly synchronized.** SDL says "reads and writes in compute
passes are NOT implicitly synchronized" (`SDL_gpu.h:3653-3661`). Across dispatches within
one pass there is "no guarantee of which order the writes will occur" (`:3775-3779`). A
peripheral whose dispatch depends on an earlier dispatch's output must end the compute pass
and begin another.

**Size caps.** SDL buffer sizes, upload offsets and upload sizes are `Uint32`. So one
column's destination buffer and one upload region are each limited to 4 GiB: 2³⁰ entities at
4-byte elements, far above any planned world size. The generator asserts this rather than
truncating.

**Device loss ends the session.** A lost GPU device is logged at `critical`, and the engine
enters `failed` (`design_python_api.md` §2). There is no recover-and-re-upload path, and
none is planned. The GPU is peripheral-domain, so core state is untouched, nothing related
to determinism is lost, and the session can still be replayed.

**Publish cost.** A snapshot *publish* gathers the rows matched by the engine view's row predicate
(`design_engine_core.md` §3.1, §3.4). Its cost, a scan over the live chunks plus a gather
over matched rows, is sim-thread work under the projection budget of that section.

### 5.1 Snapshot = projected container instance, read-only

A snapshot is a container instance, generated from a projection of the world schema. This
section states that rule and what follows from it: publish is a generated kernel, snapshots
are dense and carry ids, and nothing but the publisher can write them.

**Design rule: a snapshot is a container instance.** It is not a custom bundle of float
arrays that the container happens to produce. The same reflection generator stamps it out
from a *projected descriptor*: the `[[=viz]]` members of the world schema, with the type
mapping `fixed<> → float` applied. There is one container *mechanism*, never one container
*instance*.

- **Same machinery on both sides of the boundary.** The snapshot instance gets the same
  `column<T>` buffers (alignment, padding, chunking), the same generated `for_each` and
  accessors, and the same name catalog as the core container. The Python array view metadata
  (`design_python_api.md` §7.2), the storage-buffer staging copy (§5) and the mod-facing
  column catalog (§7.2) all describe this one instance. No separate "snapshot format" exists
  anywhere.
- **Publish is a generated kernel.** It covers the rows matched by the engine view's row predicate
  and the columns the engine view declares (`design_engine_core.md` §3.1, §3.4), in three steps:

  1. **Mask.** The live bitmap ANDed with the row predicate. A chunk whose live count is 0
     is skipped.
  2. **Scan.** An exclusive scan over the mask gives every matched row its snapshot row.
  3. **Gather.** Each declared column is copied into the engine view's writable block, converted
     from fixed-point to float.

  Every destination is a pure function of the mask, computed before anything is written, so
  the gather may run in parallel and in any order. The block's `snapshot_tick` is the only
  version a reader sees. There is one kernel per distinct projection spec, not one per engine view.
- **Blocks are reserved, not grown.** An engine view's matched rows can change on every publish, up
  to the engine view's **maximum rows**: its object type's cap, unless the engine view declares fewer. Each
  block reserves address space for that maximum and commits pages as matched rows reach
  them, so a block's address never changes (`design_engine_core.md` §3.1). How an engine view declares its
  maximum is open ([Q39](open_question.md#q39-the-gpu-allocator-for-growing-worlds)).
- **Dense, and carrying the id column.** Core storage has holes (§2.2), but publish gathers
  only live rows, so a snapshot has none: no validity bitmap, no wasted bandwidth, and every
  projected row is real. A snapshot row is a position in that one snapshot. An erase or
  create shifts every later row, so nothing may be inferred from row position across
  snapshots. Identity travels as the id column, which publish synthesizes from slot and
  generation. Snapshot rows are in slot order, so the id column is sorted ascending for
  every object type. A reader reads row `r`, takes `id[r]`, and names *that* id in any
  command. Whether every engine view carries the id column is open
  ([Q5](open_question.md#q5-is-the-id-column-in-every-projection)).

  **Ids stay aligned across the boundary**: the id read from a tick-N snapshot is the id a
  command targets. The core resolves it when the command is consumed, at the tick it names.
  It uses the pool's lookup (§2.2): the id's slot is the row, and the entity is alive only
  if the slot is live and its generation matches. Admission never reads core state. **If the id is not found, the command is deterministically rejected.** That is an
  application-time rejection, reported through the command's outcome (`design_python_api.md`
  §7.1). It is a normal result, since reaction latency means the entity may be gone by the
  time the command runs (`design_engine_core.md` §6). No id value is issued twice (§2.2), so
  a command can never silently land on a different entity from the one it named.
- **Read-only, enforced by the generator.** No reader ever needs a mutable snapshot, so the
  snapshot instance has no mutating API at all: setters, `create`/`delete` and relationship
  rewiring are not emitted for it. Immutability is a property of the generated type, not a
  convention. The only writer is the publisher, at tick boundaries. How that write path is
  defined and named is open ([Q40](open_question.md#q40-naming-the-publishers-write-path)).
  Every reader (renderer, Python, AI, mod peripherals) gets `const` access.
- **Tier 3 mods never touch snapshots.** Inside the tick they read and write *live* columns
  through the C ABI table (§7.3). A snapshot would be a stale, lossy copy of state they
  already reach at full fidelity. If a mod ships an async peripheral half (a planner, a
  neural-net brain), that half reads snapshots and emits commands, like any peripheral. It
  gets no special access.
- **Peripheral scratch state gets its own instances.** Peripherals that want writable,
  container-shaped data (per-entity AI scores, viz-derived columns, analytics accumulators)
  instantiate the same generated machinery over their *own* float-typed descriptors. These
  are keyed by the same entity ids, in the float domain.

| Instance | Domain | Column types | Mutable by |
|---|---|---|---|
| Core world container | deterministic | fixed/int | tick systems only (phased commit, including Tier 3 mods) |
| Snapshot instances (engine view blocks) | boundary | float | the publisher only; readers get `const` access |
| Peripheral containers | float | float | the peripheral that holds them, freely |

## 6. flecs boundary

The reflection-generated container is the "custom SoA tables" of `design_engine_core.md`
§4.5, for the deterministic hot path. flecs 4.1.5 is already a dependency but is not used in
code. It remains optional for cold-path entity bookkeeping, editor and debug queries, and
composing peripherals. If the sim world turns out to be the only entity population, flecs
can be dropped rather than integrated. Whether to keep it is open
([Q56](open_question.md#q56-keep-or-drop-flecs)).

## 7. Mod interaction (Python logic mods, DLL core mods)

**The container itself is never a mod API**, a rule that comes from `design_modding.md`.
Each tier gets a different generated surface over it. The schema identity goes into session
identity and the replay header, so a replay knows which world shape produced it. It covers
the descriptor layout hash, the registered dynamic columns (§7.3) and the content hashes.

| Tier | Reads the container through | Writes the container through | Sees container types? |
|---|---|---|---|
| 1 Content | nothing (it *is* the initial column contents) | loading at session start only | no, only names and types |
| 2 Logic (Python) | snapshot array views (zero-copy ndarray) | commands only | no |
| 3 Core (`.so`/`.dll`) | C ABI column table, inside declared phases | phase-structured commit, C ABI | no, only raw pointers and extents |

### 7.1 Tier 1 content mods: fixed schema, prototype tables

Compile-time reflection means the schema is fixed when the engine is built. Content mods
cannot add columns, just as with dcon's generated header. That is a feature, not a
limitation, if the schema is designed the Factorio way. Content defines **prototypes** (unit
types, recipes, stats). They are loaded into dedicated prototype tables before the freeze,
and deterministic C++ systems interpret them (`design_modding.md` §1: "data interpreted by
deterministic C++ systems, not code").

Reflection helps here too: the descriptor structs *are* the content-validation schema. The
loader can be generated (property names, types, ranges, required or optional). So
declarative content (JSON or TOML) is validated against the same single source of truth as
everything else, and its hash goes into session identity.

Truly new state, a new column, is by definition Tier 3 or an engine change (§7.3).

### 7.2 Tier 2 Python logic mods: generated snapshot catalog + commands

Logic mods live outside the determinism boundary and use exactly two artifacts
(`design_modding.md` §2). The container's job is to make both of them *generated*:

- **Reads.** `snap.column("pop.wealth")` (`design_python_api.md` §7.2). The name-to-column
  catalog, the fixed-to-float projection at publish and the nanobind array view metadata
  (dtype, extent) are all stamped out from the `[[=viz]]` descriptor members. They all
  describe the read-only snapshot instance (§5.1). A mod can list the catalog at runtime.

  **Column read capabilities are enforced at the `ModContext` API on every mod host.** The
  catalog is filtered to the mod's capabilities, and a `snap.column(...)` outside them
  raises `ColumnNotGrantedError` (`design_modding.md` §4.1, §4.3). On the thread host this
  is not a security boundary: Python in-process can reflect into anything, the same
  precedent as core-mod capabilities (`design_modding.md` §5.4). The API check keeps the
  observable surface the same on both mod hosts. On the process host the enforcement is also
  physical. That mod's engine view is projected from the columns its capabilities allow, straight
  into its own shared-memory segment, so its mapping contains nothing else
  (`design_modding.md` §4.3). This applies once process-host engine views exist; they are deferred
  together with the `SHARED` engine view (`design_engine_core.md` Appendix A). A mod that asks for
  sensitive columns is a policy signal to run it on the process host.

  Command capabilities are enforced at the ring on every mod host, because writes always
  cross the boundary.
- **Writes.** Commands only, validated at submission, with a bounded, explicit admission
  result (`design_engine_core.md` §5). Commands name entities by id (§2.2), and
  the generated builders enforce this by type: a row is not a valid target and cannot
  be passed as one. The command registry (`design_modding.md` §7, "new command type") is
  itself a set of descriptor structs. Reflection generates the packed layout, the validation
  skeleton and the Python builder stubs. So the **one-schema rule** (replay payload ≡ IPC
  payload ≡ Python builder) holds by construction instead of by review. The generated layout
  is the canonical encoding: explicit little-endian, fixed widths, and decoding that does
  not depend on alignment (`design_engine_core.md` §2.3). It is never a memcpy of a native
  struct. Transport envelopes (replay chunking, IPC framing) stay outside the schema.
- Python never sees a container pointer, a mutable span or a core (fixed-point)
  representation. The GIL, GC pauses and floats cannot reach world state.

### 7.3 Tier 3 DLL core mods: C-ABI column table + registered dynamic columns

Core mods run inside the tick and need direct column access. But the plugin boundary is a
versioned C ABI (`design_modding.md` §5.1). The reflection-generated container is a C++
type, and worse, one built with modules and `-freflection`, so it must never cross that
boundary. Compiler and flag drift across the boundary is what the handshake's
build-fingerprint check catches.

- **Access.** The `sim_estab_host_v1` services table exposes columns as raw memory.
  `resolve_column(object_name, property_name) → column_id` runs at session start, never at
  registration (see the rule below). The two accessors scoped to one `tick_fn` invocation
  are:

  ```c
  /* per object type, once per invocation */
  sim_estab_row_set_v1 get_row_set(uint32_t object_id);
  /*  uint64_t extent;        rows [0, extent); a row is live where its bit is set
   *  uint64_t begin, end;    this invocation's task range
   *  const uint64_t *live;   live bitmap, one bit per row (§2.2); NULL for an
   *                          append-only type, where every row below extent is live
   *  const uint32_t *chunk_live;   live count per chunk; a chunk at 0 may be skipped
   *  uint32_t generation_column;   column holding each row's generation. A row's id
   *                          is (row << 32) | generation[row], the only identity a
   *                          mod may retain or put in a command                      */

  /* per column */
  sim_estab_column_view_v1 get_column(uint32_t column_id);
  /*  void    *data;          row 0; writable only if WRITABLE is set
   *  uint32_t elem_size, flags;              flags: WRITABLE
   *  uint64_t read_begin,  read_end;         set from the declared access kind
   *  uint64_t write_begin, write_end;        empty unless WRITABLE
   *  uint64_t read_end_simd; read_end rounded up to the lane multiple: readable
   *                          memory whose values are unspecified, so any result
   *                          computed from those lanes must be masked out (§1.2)    */
  ```

  Note what is not there. There is no cap, because handing out an allocation bound invites
  reads past the extent. `read_end_simd` covers the one legitimate use (dcon's tail-free
  loops), and its name states the masking obligation. The omission has a second purpose. A
  mod can read neither the cap nor the committed memory, so **pool fullness never becomes
  an input to mod logic**. A mod learns only that a create was refused, and only when a cap
  is reached. The extent is there because scans need it. It is state, the same on every
  machine. Also, the read span is scoped, not the full extent (next bullet).

  **Two lifetimes apply here, and they are not the same length.** Confusing them is how a
  mod ends up correct by luck:

  - A resolved pointer or column span is valid for this `tick_fn` invocation only. Keeping
    one across phases breaks the contract even though no row moved, because the permission
    itself changes. The spans are recomputed per phase, staged buffers merge at each
    boundary, and a `write_dbl` column's front and back swap there.
  - A row is valid for the whole tick, and rows never move (§2.2). But after a terminal
    commit the row may hold a different entity, and a bare row cannot tell. So a mod may
    carry a row from one phase to the next within a tick, and must resolve the column span
    again to use it.

  Neither survives the tick. Anything a mod keeps longer, or writes into a command, is an
  id.

  The C ABI accessor implementations and the stable (object, property) → column id mapping
  are generated from the descriptors. The mapping is sorted by name, never by declaration or
  hash order. Type identity, including the fixed-point representation and scale, is checked
  at resolve time, not assumed.

  **Column ids are assigned when the column set closes, and resolving before that is an
  error.** Sorting by name is stable only over a *closed* set. The set stays open as long as
  any core mod may still register a dynamic column (below). A mod that resolved `pop.wealth
  → 7` during its own registration would find column id 7 meaning a different column after
  the next mod registered `pop.aaa`. The type check would still pass, and the mod would
  write into the wrong column inside the deterministic core: silent, deterministic,
  reproducible corruption. Hence:

  | When | `register_column` | `resolve_column` |
  |---|---|---|
  | registration (`sim_estab_mod_register_v1`) | legal | **error**: the set is open |
  | session start (`on_session_start`, at the freeze) | error: the set is closed | legal, and the column id is stable for the session |

  Registration, session start and the callback are defined in `design_modding.md` §5.1. The
  freeze that runs between them is in `design_engine_core.md` §2.4.

  **There are two column id spaces, not one.** Compile-time columns keep column ids `[0,
  N_static)`, sorted by name from the descriptors and independent of what any mod does.
  Otherwise installing a mod would renumber every generated accessor and break the typed
  fast path below. Dynamic columns get column ids `[N_static, N_static + K)` at the freeze,
  sorted by name within the dynamic set. Both halves are therefore independent of
  registration order. So the schema identity hash can cover the dynamic list without also
  hashing the order in which mods happened to load.

  **Relationship links cannot be resolved as columns.** `resolve_column` covers data
  properties only. Links are stored as slots of another object type (§2.2). Exposing them
  raw would hand a mod a row *into a different object type*. This ABI
  has no vocabulary for that: `get_row_set` describes one object type, and a span means
  nothing against another. Mod-facing link traversal is therefore out of scope for v1
  ([Q58](open_question.md#q58-mod-link-traversal)). Adding it means designing that
  vocabulary (an accessor for another type's row set, and what a task range even means on
  the far side), not exposing another column id. Core mods that need relationship data get
  it as a derived data column, maintained by a built-in system.

- **The spans are the permission.** A mod system declares an access kind per column at
  registration: `read_full`, `read_local`, `write_local`, `write_staged` or `write_dbl`
  (`design_engine_core.md` §4.1). The engine computes `read_begin/read_end` and
  `write_begin/write_end` from that declaration and the phase the scheduler placed the
  system in. A mod does not have to follow a paragraph about which rows it may touch: it is
  handed exactly those rows. In particular, no one can declare `write_local` on a column
  that any system in the phase reads across ranges. So the read span a mod receives never
  shows rows that another task is writing at the same time.

  Declarations place mod systems in the phase-structured scheduler like any built-in system:
  alone in a phase by default, in parallel when the declarations allow (`design_modding.md`
  §5.1). Operations that may conflict or change structure take `write_staged`: shared
  claims, reductions that are not order-independent, create and delete, relationship
  rewiring, and any write whose destination is found at run time. They go through
  engine-held buffers merged in fixed order (`design_engine_core.md` §4.1). The C ABI limits
  *what* is reachable; certification (`design_modding.md` §5.3) checks *how* it behaves.
- **Mod state: registered dynamic columns.** This is the one real schema-extension path.
  Before session start, a core mod may register extra columns with `register_column(object,
  name, type_tag, flags)`. `type_tag` is a closed enum of approved column types (`i32`,
  `i64`, `fx32_16`, `fx64_32`, `bitfield`, …). `flags` carries the same annotations
  compile-time columns get (`saved`, `viz`, …). How `bitfield` columns are made canonical is
  open ([Q29](open_question.md#q29-how-are-bitfields-made-canonical)).

  The container holds them as type-erased `column` buffers, with the same alignment, padding
  and chunking as compile-time columns. The tag selects the checksum, serialization and
  fixed-to-float projection kernels from a fixed generated table. So *registered* mod state
  is truly inside the per-tick checksum, serialization and snapshot machinery, not just its
  memory. The shape of the snapshot part that holds dynamic `viz` columns is open
  ([Q41](open_question.md#q41-dynamic-viz-columns-in-snapshots)).

  This is a guarantee of contract and certification, not physical containment. Native mods
  have full process access (`design_modding.md` §5.4), and could keep undeclared global or
  heap state that the checksum never sees. Doing so breaks the determinism contract
  (`design_modding.md` §5.2), and certification looks for it. Registration makes compliance
  easy; it does not make omission impossible. The restriction to approved types is
  intentional: arbitrary blobs inside the determinism boundary could not be audited.

  **There is no cap on dynamic columns per object type** (`design_limits.md` §4).
  Attribution takes its place: registered dynamic columns are counted and reported per
  (object type, mod), so the cost a mod adds is named even though nothing refuses it. The
  count is taken at registration, because that is where the cost is incurred. Every column
  of a type is reserved at the cap, zeroed at every erase and written at every create
  (§2.2). So a mod registering dynamic columns raises the memory and per-entity cost of a
  core object type. That is a third party quietly raising engine cost, which this design
  requires to be bounded and attributable. Without a
  cap the cost is not bounded, so attribution carries the whole weight: the per-(type, mod)
  count is the control itself, not a diagnostic extra. Where the count is reported is open
  ([Q36](open_question.md#q36-where-are-per-type-mod-attribution-counts-reported)).

  Type checking at resolve time, representation and scale included, applies to dynamic
  columns as to compile-time ones. Registered columns are part of the schema identity hash.
  No registration is allowed after session start, for replay identity: the set closes at the
  freeze, which is also where column ids are handed out (`design_engine_core.md` §2.4 step
  1).

  **A name collision is a load failure, not a merge.** Two mods registering the same
  `(object, name)` raise `ModLoadError` naming both (`design_modding.md` §6), even when the
  type tags agree. Silently sharing one column would create a hidden data coupling between
  two separately certified mods, *inside* the determinism boundary, and certification of
  either mod would not test for it. By convention, dynamic column names are namespaced by
  mod id (`example.traffic.heat`).
- Compile-time columns keep their typed SIMD-kernel fast path. Dynamic columns pay the
  type-erasure cost only in *mod* systems. Built-in systems are unaffected.

### 7.4 Rules summary

These rules from §2 to §7 apply at every tier.

- The container is internal to the engine. Every mod-facing surface (catalog, command
  registry, C ABI table) is generated from the same descriptors.
- Schema identity = descriptor hash + dynamic-column registrations + content hashes,
  recorded in session identity and the replay header.
- No schema change after session start, at any tier.
- Snapshots are read-only at every tier, and the publisher is the only writer (§5.1). Tier 3
  mods work on live columns and never read snapshots inside the tick.
- All world state a mod can reach lives in columns held by the container, so it is
  checksummed, serialized and snapshotted in one uniform way. This is a contract rule for
  Tier 3 code, enforced by certification and trust. It is not a physical guarantee against
  native code (§7.3).
- **Rows never move; only ids leave the core** (§2.2). A bare row cannot tell a new
  occupant of its slot from an old one, so it never crosses a boundary: not in a command,
  not in a mod's storage past the tick, not in a savegame, not in a GPU buffer read in a
  later frame. Anything held past the tick is an id. Resolved *column spans* last even less:
  one `tick_fn` invocation (§7.3).
- **Reads are scoped, not just writes.** Every tier gets an extent computed from its
  declared access kind: one writer per column per phase, and no cross-range read of a
  `write_local` column (`design_engine_core.md` §4.1). Every tier sees the same live bitmap.
  A read path masks dead rows, and only an append-only type lets it skip the mask.
- **Every object type has a cap** (§2.1, §2.2): 2²⁴ unless declared, at most 2³²−1. Memory
  is reserved at the cap and committed as the pool fills, and addresses never move. Commit
  failure ends the session and is never a rejection. A cap fixes its accepted set by merge
  order, and every cap joins session identity. What a create at the cap *does* depends on
  the kind of cap. A game-rule cap rejects deterministically and reports. A ceiling is an
  error and stops: the simulation for an engine system, or the mod whose system it is
  (§2.2). The ceiling reading is the default
  ([Q31](open_question.md#q31-what-does-hitting-a-declared-cap-do)). No tier can read the cap
  or the committed memory, which is why a cap that a mod can reach must be declared as a game
  rule.
- **Id lookup is O(1) for every object type** (§2.2). The slot is the row, and the
  generation says whether the entity is still there. A snapshot's id column is sorted for
  every object type (§5.1).
- **GPU destination buffers are sized per engine view** (§5), from the engine view's maximum rows. How an
  engine view declares that maximum is open (`design_limits.md` §7;
  [Q39](open_question.md#q39-the-gpu-allocator-for-growing-worlds)).

## 8. Risks and open questions

This section lists the risks of the reflection-based approach and the spike results that
bear on them. Open questions are tracked in [open_question.md](open_question.md).

- **`-freflection` is new.** GCC 16 is its first release, so expect rough edges. Two spikes
  cover the shapes this design uses:
  - A `consteval { … define_aggregate(^^pop_soa, cols); }` block of the shape in §2.1
    compiles and runs under `g++ -std=gnu++26 -freflection` in a plain translation unit.
  - **Reflection inside C++20 module interface units works, under one rule.**
    `define_aggregate` inside a `.cppm` works, and the generated struct is a complete,
    usable type across `import`. An exported `consteval` helper evaluated in the importing
    translation unit fails with "couldn't look up 'std::vector'". The generator's
    `std::vector`, included in the module's global module fragment, is not reachable where
    the importer evaluates the helper. The module itself compiles, so the failure appears
    only in the importer. Including the generator's headers in each consumer works around
    it, but leaks `<vector>` and `<meta>` into every consumer, so it is not used.

  **Rule: the module materializes its reflection results and exports only concrete types and
  `constexpr` values.** No `consteval` body is evaluated again in a consumer. This is the
  split the compile-time bullet below recommends, and it is also required for correctness.
  What the spike tested is narrower: that no `consteval` function is evaluated in an
  importing unit. Its module still exported a template and `consteval` helpers. The spike
  was built with bare `g++-16 -fmodules`; building the same shape through the Conan/CMake
  module build is not yet verified (`TODO.md`, M3).
- **Compile time.** Reflection-heavy code has a measurable cost (Vittorio Romeo's
  measurements, in the references). Contain it: put the descriptors and the generator in one
  module partition, and export the generated containers as concrete types.
- **MSVC has no announced date for reflection, and the build makes the gap explicit.** Conan
  restricts `msvc.cppstd` to `[null, 14, 17, 20, 23]`, so C++26 cannot even be expressed on
  the Windows profiles. They are pinned at `cppstd=23`, while Linux uses `gnu26`. Windows
  therefore cannot compile this design at all, whatever MSVC's own P2996 support. The
  Windows profiles may need to work before MSVC ships P2996. The options then are GCC on
  Windows, Bloomberg's clang-p2996 fork, or a temporary fallback: descriptors compile as
  plain structs, and containers are written by hand. This is the largest strategic risk of
  the reflection-based approach ([Q34](open_question.md#q34-windows-and-c26)).
- **`std::simd` coverage.** Core arithmetic is verified, and `<simd>` is present. Under
  `-march=x86-64-v3`, `vec<int64>` has 4 lanes and `vec<int32>` has 8 (§3). Fixed-point
  multiply-high patterns and gather/scatter ergonomics are unproven. Prototype the `fixed<>`
  SIMD kernels early, and keep Highway as the fallback
  ([Q30](open_question.md#q30-is-stdsimd-enough)).
- **GCC `<meta>` API drift.** GCC's signatures differ slightly from the paper. `remove_cv`
  and `dealias` need explicit `std::meta::` qualification, because argument-dependent lookup
  does not find them from an `info` argument. The paper's `type_remove_cv` is spelled
  `std::meta::remove_cv` in libstdc++ 16. Wrap all `std::meta` use behind a small internal
  header, so that such changes stay in one place.
- **Dynamic columns (§7.3) when a mod is removed.** Representation and ordering are settled.
  Ordering is not registration order. Column ids are assigned at the freeze, sorted by name
  *within the dynamic set*, in their own column id space above the compile-time columns
  (§7.3). That is stronger than load order, since the same mod set gives the same column ids
  whatever order the mods loaded in. Schema evolution is still open: what happens to a
  dynamic column's data when a mod is removed from an existing save. Resolve it when
  serialization tags are designed
  ([Q59](open_question.md#q59-mod-added-column-data-when-a-mod-is-removed-from-a-save)).

## 9. Suggested next steps

These steps fill build-order step 3 of `design_engine_core.md` §7, in this order.

1. **`column<T>`**, the aligned, padded buffer, plus a `fixed<>` SIMD kernel prototype on
   `std::simd`, including one Qm.n multiply-high kernel and one tagged-id gather.
2. **A minimal generated container**: one append-only object type in a pool, typed ids,
   accessors, `for_each` and a checksum visitor. This proves the shape of the
   generator. It follows the module rule of §8: export concrete types and `constexpr` values
   only.
3. **Chunked parallel-for** over the container with OpenMP. Verify that 1 thread and N
   threads give the same checksums (the harness of `design_engine_core.md` §2.3).
4. **Snapshot projection**: `[[=viz]]` columns to float arrays to storage buffers (SSBOs),
   through the existing GPU context. The generated GLSL declarations round-trip through
   glslang.
5. **Erase and slot reuse.** The live bitmap and chunk live counts, the generation bump and
   retirement, lowest-free create from the bitmaps, row zeroing, and the two steps of the
   terminal commit (§2.2). Then the first relationship type
   ([Q32](open_question.md#q32-relationships)) and serialization tags. A save holds the
   extent, the bitmaps and the generations (§2.2), so the tag design has to carry them.
6. **Mod surfaces last**, once the shapes are stable: the generated snapshot column catalog
   (Tier 2), then the C ABI column table with resolve and handshake (Tier 3), then dynamic
   column registration.
